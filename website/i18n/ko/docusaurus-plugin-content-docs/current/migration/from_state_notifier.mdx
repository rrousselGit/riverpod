[Riverpod 2.0](https://pub.dev/packages/flutter_riverpod/changelog#200)과 함께 새로운 클래스인
`Notifier` / `AsyncNotifier`가 도입되었습니다.
이제 `StateNotifier`보다는 이 새로운 API를 사용하는 것이 권장됩니다.

이 페이지에서는 더 이상 사용되지 않는 `StateNotifier`에서 새 API로 마이그레이션하는 방법을 설명합니다.

`AsyncNotifier`가 가져온 가장 큰 이점은 향상된 `async` 지원입니다.
`AsyncNotifier`는 UI에서 상태를 변경할 수 있는 방법을 노출하는 `FutureProvider`라고 생각할 수 있습니다.

또한 새로운 `(Async)Notifier`는 다음과 같은 특징이 있습니다:

- 클래스 안에서 `Ref` 객체를 노출합니다
- 코드 생성을 사용할 때와 사용하지 않을 때의 문법이 비슷합니다
- 동기 버전과 비동기 버전의 문법이 비슷합니다
- 로직을 Provider에서 떼어 내 Notifier 자체에 모읍니다

`Notifier`를 정의하는 방법과 `StateNotifier`와의 차이, 그리고 비동기 상태를 위해
새로운 `AsyncNotifier`로 마이그레이션하는 방법을 살펴보겠습니다.

:::tip
다음은 `StateNotifier<AsyncValue<T>>`에서 `AsyncNotifier<T>`로 마이그레이션하는 과정을 요약한 것입니다:

- 초기화 로직을 `build`에 넣습니다
- 초기화나 부수 효과 메서드에 있는 `catch`/`try` 블록을 모두 제거합니다
- `build`에서 `AsyncValue.guard`를 모두 제거합니다. `build`가 반환한 `Future`는 자동으로 `AsyncValue`로 변환되기 때문입니다
:::


### 장점 {#advantages}

몇 가지 예제를 살펴봤으니, 이제 `Notifier`와 `AsyncNotifier`의 주요 장점을 정리해 보겠습니다:
- 새 문법은 특히 비동기 상태에서 훨씬 단순하고 읽기 쉽습니다
- 새 API는 대체로 보일러플레이트 코드가 적습니다
- 어떤 종류의 provider를 작성하든 문법이 통일되어, 코드 생성이 가능해집니다
(<Link documentID="concepts/about_code_generation" /> 참고)

더 나아가 다른 차이점과 공통점도 살펴보겠습니다.

## 생명주기 동작이 다릅니다 {#lifecycles-have-a-different-behavior}

`Notifier`/`AsyncNotifier`와 `StateNotifier`는 생명주기가 크게 다릅니다.

이 예제는 기존 API의 로직이 얼마나 흩어져 있는지 다시 한번 보여 줍니다:

<AutoSnippet raw={oldLifecyclesOld}/>

여기서 `durationProvider`가 갱신되면 `MyNotifier`는 *폐기*되고, 인스턴스가 새로 생성되며
내부 상태도 다시 초기화됩니다.  
게다가 다른 모든 provider와 달리 `dispose` 콜백을 클래스 안에
따로 정의해야 합니다.  
마지막으로 _provider_ 안에 `ref.onDispose`를 작성하는 것도 여전히 가능하므로, 이 API에서는 로직이
얼마나 흩어질 수 있는지 다시 한번 드러납니다. 개발자는 이 Notifier의 동작을 이해하기 위해
무려 여덟(8!) 군데를 살펴봐야 할 수도 있습니다!

이런 모호함은 `Riverpod 2.0`에서 해결되었습니다.

### 기존 `dispose` vs `ref.onDispose` {#old-dispose-vs-refondispose}
`StateNotifier`의 `dispose` 메서드는 notifier 자체의 폐기 이벤트를 가리킵니다. 즉,
*자기 자신이 폐기되기 전에* 호출되는 콜백입니다.

`(Async)Notifier`에는 이런 속성이 없습니다. *다시 빌드될 때 notifier 자체는 폐기되지 않고*,
*내부 상태*만 폐기되기 때문입니다.  
새 notifier에서는 다른 모든 provider와 마찬가지로 `ref.onDispose`(및 기타 메서드)를 통해
*한곳*에서만 폐기 생명주기를 처리합니다.
이렇게 API가 단순해지고 개발 경험도 좋아져, 생명주기와 관련된 부수 효과를 이해하려면
`build` 메서드 *한곳*만 보면 됩니다.

요약하면, *내부 상태*가 다시 빌드되기 전에 실행될 콜백을 등록하려면
다른 모든 provider처럼 `ref.onDispose`를 사용하면 됩니다.

위 코드는 다음과 같이 마이그레이션할 수 있습니다:

<AutoSnippet
  language="dart"
  {...oldLifecycles}
  translations={{
    period: `    // 코드를 여기, 한곳에서만 읽고 쓰면 됩니다`,
    update: `    // \`mounted\`는 더 이상 없습니다!
    state++; // 예외가 발생할 수 있습니다.`,
  }}
></AutoSnippet>

이 코드는 확실히 단순해졌지만, 아직 해결되지 않은 문제가 있습니다.
`update`를 실행하는 동안 notifier가 아직 살아 있는지 알 수 없다는 점입니다.  
이 때문에 원치 않는 `StateError`가 발생할 수 있습니다.

### 더 이상 `mounted`는 없습니다 {#no-more-mounted}
이 문제는 `(Async)Notifier`에 `StateNotifier`에서 쓸 수 있던 `mounted` 속성이
없기 때문에 발생합니다.  
생명주기의 차이를 생각하면 당연한 결과입니다. 만들 수는 있겠지만, 새 notifier에서 `mounted`
속성은 오해를 부를 수 있습니다. `mounted`가 *거의 항상* `true`일 것이기 때문입니다.

[직접 우회 방법](https://github.com/rrousselGit/riverpod/issues/1879#issuecomment-1303189191)을 만들 수도 있지만,
비동기 작업을 취소하는 방식으로 해결하는 것을 권장합니다.

작업 취소는 직접 만든 [Completer](https://api.flutter.dev/flutter/dart-async/Completer-class.html)나
그와 비슷한 방식으로 구현할 수 있습니다.

예를 들어 네트워크 요청에 `Dio`를 사용한다면 [cancel token](https://pub.dev/documentation/dio/latest/dio/CancelToken-class.html)을
사용해 보세요(<Link documentID="concepts2/auto_dispose" />도 참고하세요).

따라서 위 예제는 다음과 같이 마이그레이션됩니다:
<AutoSnippet
  language="dart"
  {...oldLifecyclesFinal}
  translations={{
    period: `    // 코드를 여기, 한곳에서만 읽고 쓰면 됩니다`,
    codegen_cancel: `    // \`cancelToken.cancel\`이 호출되면 커스텀 Exception이 발생합니다`,
  }}
></AutoSnippet>


## 상태 변경(mutation) API는 이전과 같습니다 {#mutations-apis-are-the-same-as-before}

지금까지 `StateNotifier`와 새 API의 차이점을 살펴봤습니다.  
반면 `Notifier`, `AsyncNotifier`, `StateNotifier`에 공통된 점은 상태를
사용하고 변경하는 방식입니다.

consumer는 세 provider 모두에서 같은 문법으로 데이터를 가져올 수 있으므로,
`StateNotifier`에서 마이그레이션할 때 매우 편리합니다. notifier 메서드도 마찬가지입니다.

### 테스트에서 `.debugState` 마이그레이션 {#from-debugstate-in-tests}

`StateNotifier`는 `.debugState`를 노출합니다. 이 속성은 pkg:state_notifier 사용자가 개발 모드에서
테스트를 위해 클래스 바깥에서 상태에 접근할 수 있도록 하는 데 쓰입니다.

테스트에서 상태에 접근하려고 `.debugState`를 사용하고 있다면, 이 방식은 버려야 할 가능성이
높습니다.

`Notifier` / `AsyncNotifier`에는 `.debugState`가 없습니다. 대신 `@visibleForTesting`으로 지정된
`.state`를 직접 노출합니다.

:::danger 경고
테스트에서 `.state`에 접근하는 것은 피하세요. 꼭 필요하다면, `Notifier` / `AsyncNotifier`가 이미
제대로 인스턴스화되어 있는 경우에 _한해서만_ 그렇게 하세요.
그런 경우라면 테스트 안에서 `.state`에 자유롭게 접근해도 됩니다.

실제로 `Notifier` / `AsyncNotifier`는 직접 인스턴스화해서는 _안 되며_, 반드시 해당 provider를
통해 다뤄야 합니다. 그렇지 않으면 ref와 family 인자가 초기화되지 않아
notifier가 *제대로 동작하지 않습니다*.
:::

`Notifier` 인스턴스가 없나요?  
문제없습니다. 노출된 상태를 읽을 때처럼 `ref.read`로 인스턴스를 얻을 수 있습니다:

<AutoSnippet
  raw={obtainNotifierOnTests}
  translations={{
    notifier: `    // notifier 가져오기`,
    state: `    // 노출된 상태 가져오기`,
    test: `    // TODO 테스트 작성하기`,
  }}
/>

테스트에 대해서는 전용 가이드에서 더 알아보세요. <Link documentID="how_to/testing" />를 참고하세요.
